## F3 Explainability [F3]
Approved 2026-11-02 with: which features each model relies on (global), and why one prediction came out as it did (local), in the trainer, on the saved runs' page and in the CLI, without SHAP (the plan's first idea). Decisions:
- **Global: permutation importance**, the method of scikit-learn's `sklearn.inspection.permutation_importance`: the values of one feature are shuffled and the drop in macro-F1 is measured, the same way for the 11 models, so their numbers can be set side by side. It shuffles the columns the user chose (before one-hot encoding), so there is one number per feature. The models' own `feature_importances_` and `coef_` are not shown: not every model has them, and a tree's favour features with many values
- **On the test split only** (what the model relies on in rows it never saw); above 5,000 rows a stratified sample of 5,000 (`stratified_positions`, at least 3 per class) with the run's evaluation seed; 5 repeats; shown as the mean ± std of the drop, features ranked by the mean. The test split is reused after the evaluation: the result is a diagnosis, never a way to choose features, models or hyperparameters (HC1)
- **On demand, not after every training:** a job with progress (one step per feature) and Cancel, on the training's own queue (RD2); it is worked out one feature at a time so the job can advance and stop, and a test checks the numbers are scikit-learn's own. For one of the run's models, the selected one by default, and only for the workspace's run (RD3)
- ~~**A warning when one feature carries most of the effect** (more than half of the summed positive drops): check that it is not a copy of the label~~ **Superseded by HC2:** an importance concentration warning when one feature carries more than half of the summed positive drops; a label copy is one possible cause
- ~~**Kept with the run:** in the session until the next training; computed before Export, it is written in the TrainingRun record (and so in the bundle's copy of it), shown on the saved runs' page and by `ids --info`. The record's new keys are optional: `SCHEMA_VERSION` and the bundle's `FORMAT_VERSION` stay 1, and a record or a bundle without them still opens~~ **Superseded by RD3 and RD4:** a file of its own per run and model, `<run id>.importance.<model id>.json`, kept until the run is deleted, shown on the saved runs' page and by `ids --info`; the record and the bundle are not changed
- **Local: the typical value in place of the real one.** For each feature of the row, its value is replaced by the feature's typical value in the training split (the median of a number, the most frequent value of a category) and the change in the predicted class's probability is measured: positive pushes toward the class, negative away from it. One prediction of a small table, so it is immediate. It is an approximation, not SHAP, and the page says so; a model without probabilities gets no explanation, and the page says why. The limits are shown beside the result (HC2): approximate, not causal; correlated features share the effect; one feature changed alone can make a row that never occurs; the probabilities are not calibrated
- **Shown under "Make a Prediction"**, with every single prediction (a CSV prediction gets none): the 5 features that push most toward the predicted class and the 5 that push most away, each with its value and the typical value
- **The typical values are written in the record at training time.** A bundle saved before F3 falls back to the medians the pipeline learnt (its `SimpleImputer`), for the numbers only; its categorical features get no explanation, and the page says so
- **The CLI:** `ids --info` shows the top features when they were computed; the interactive prediction shows the top 3 reasons; `--json` adds `why`
- **No new dependency**, nothing new sent anywhere: everything is computed on this computer from the run's own rows

## H Hardening after the review [H]
Approved 2026-11-02. An outside review of v5.0–v5.3 (architecture, security, ML validation) set conditions for calling v5.3 complete. Its order: **Correctness → Security → Reliability → Usability → Features**. The review's two misreadings were settled, and their facts were kept as they are: the official NSL-KDD files are used as published by default, and the strict mode that removes the 610 overlapping rows is an explicit choice; the gap between accuracy and macro-F1 is explained in `docs/report/FINDINGS.md` §3. The IDs carry an H so they don't clash with the plan's (R3, S12…). Rules:
- **Secure the functions, never remove them:** `toolkit web --host ADDRESS` and the remote trainer and scanner keep everything they do today. No private address is refused; scanning inside the networks the user may scan is the scanner's purpose
- **The simplest fix that closes the risk:** no enterprise RBAC, no durable job queue, no distributed task system, no new dependency
- **Each task names its problem, its severity, the fix, the tests and when it is done.** "To check first" marks a fact that was not yet read in the code when the task was written
- **Test levels are named** in the docs: unit, integration, end-to-end, manual verification. A count of tests is not a measure of readiness
- **Severity, test levels and "done" are defined in [DECISIONS.md](../ai_brain/DECISIONS.md)**; the designs these tasks build (RD1–RD4) are in [REVIEW_DECISIONS.md](../ai_brain/REVIEW_DECISIONS.md): a task here says what to do, those files say the rules it must keep

**The gate 5.3 conditions (from the review):** (1) remote access and the remote scanner kept, with the risks of the access closed (HS1–HS3); (2) real control of the outside connections (HS4); (3) the limits of the ML evaluation and of the explanations documented (HC1, HC2); (4) the importance kept with its `run_id` (HR2, HR5); (5) a shared limit for the heavy jobs (HR1); (6) a defined behaviour on a sudden stop, and the history managed (HR3, HR4); (7) real use shown: a user who is not the developer, and Linux and macOS before they are called supported (HV1–HV3).

**Order:** HC → HS → HR (HR3 first: the others publish through its module) → HV1–HV3 → F3d–F3g → F5, F6 and the rest of the plan. HV1 needs a tester and HV2 needs a push; both are the user's to arrange, and the user decides whether F3d waits for them.
